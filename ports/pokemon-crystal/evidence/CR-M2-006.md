## Reference interpretation

Pan Docs was used first:

- the CGB boot ROM owns the volatile handoff state and jumps to cartridge
  address `$0100`;
- `DIV` is the visible portion of the continuously running system counter;
- STAT sources share an edge-triggered interrupt line;
- CGB HDMA transfers have explicit block and HBlank semantics; and
- MBC3 RAM/RTC selection, latching, and registers are cartridge hardware,
  separate from the CPU timer.

The pinned SameBoy implementation was then used as the proven independent
implementation. Its Core executes the source-built CGB boot ROM, models the
PPU/timer/HDMA/MBC3 independently, and preserves cartridge RTC state across a
console reset. The port oracle uses only public/Core state and callback APIs;
it does not link GB Recompiled runtime code.

## Results

Repository evidence:

- root build completed with no work remaining;
- focused CGB/timing/device CTest selection: 7/7 passed;
- complete repository suite: 41/41 passed;
- external timer selection: 13/13 passed;
- external LCD/STAT selection: 4/4 passed, including the CGB case;
- external CGB selection: 1/3 passed.

The two CGB failures are `boot_div-cgb0` and `boot_div-cgbABCDE`. They reproduce
the documented limitation in `GBC.md`: GB Recompiled starts generated games
from configured post-boot state and does not emulate any boot ROM, so it cannot
claim the revision-specific internal DIV value produced by those boot ROMs.
`boot_regs-cgb` passes. This is a bounded, named boot-handoff limitation, not
an unexplained Crystal route difference.

The independent comparison passed:


| Checkpoint | Frame comparison | State comparison |
| --- | --- | --- |
| Title | SameBoy 770 vs generated 750; only two title-sparkle pixels differ | not asserted |

| Overworld | same frame; exact outside the animated 22×16 player-sprite rectangle | PC, SP, and 7 WRAM anchors exact |

Raw RGB bytes are not compared directly because the two renderers expand a
5-bit CGB palette component differently (`65` vs `66`, for example). The
comparator losslessly maps both outputs back to `round(component * 31 / 255)`.
After that normalization:

- the new-game and Continue images are byte-for-byte equal;
- the title has exactly two differing sparkle pixels at `(77,18)` and
  `(93,18)`;
- the overworld has 256 differing pixels, all confined to `(35,60)-(56,75)`,
  the player-sprite animation region; the entire background and inspected
  machine/game state agree.

The title/new-game host-frame offsets are expected because SameBoy executes
its source-built boot ROM while GB Recompiled begins from configured post-boot
state. They are captured as exact expectations rather than hidden by a broad
image tolerance.

The Continue result is stronger than a visual comparison: SameBoy loaded the
32,768-byte battery file produced by the generated runtime, reached the same
Continue scene at frame 1500, and agreed on PC `$0460`, SP `$C0E3`, player
status, map `26:5`, and coordinates `1,8`.

## Gate audit

- **Relevant reusable tests:** timer, LCD/STAT, CGB, HDMA, PPU/OAM DMA, MBC3
  persistence, and event-deadline tests were run. Independent Mooneye timer and
  STAT selections pass; the two CGB boot-DIV failures are named and bounded.
- **Reference order:** hardware behavior was interpreted from Pan Docs first
  and the pinned SameBoy Core second.
- **Independent Crystal checkpoints:** title, new-game, overworld, and
  save-backed Continue were replayed in SameBoy from the checked cycle inputs.
- **Frames and inspected state:** exact matches and the two narrow visual
  phase differences are encoded in a fail-closed comparator. There are no
  unexplained pixels or inspected state differences.
- **Legal/reproducible boundary:** the driver accepts only the supported user
  ROM and pinned SameBoy commit. ROM, save, executable, reference checkout,
  frames, states, and raw logs remain ignored.

## Limits

- This does not turn the shared-runtime differential test into independent
  hardware proof; SameBoy is the independent implementation used here.
- GB Recompiled still does not emulate the CGB boot ROM and still fails the two
  revision-specific boot-DIV tests. No claim is made otherwise.
- Four selected checkpoints do not prove every Crystal scene, every CGB
  register, link behavior, infrared behavior, or DMG-on-CGB behavior.
- The SameBoy comparison uses its source-built replacement boot ROM, not
  Nintendo firmware. The post-boot animation phase therefore is not expected
  to share a universal host-frame origin.
- The inspected state is deliberately narrow: PC, SP, and the route's seven
  semantic WRAM anchors. Whole-machine independent state equivalence is not
  claimed.

# CR-M4-003 — Expose a narrow port/frontend extension

Date: 2026-07-29

## Result

PASS. GB Recompiled now provides a versioned, exact-ROM port/frontend ABI for
source-built host extensions. Crystal registers the first module,
`crystal-workbench` version 1, and can show or hide its native UI while the
original guest keeps running.

The ABI is renderer-independent and does not expose SDL, ImGui, generated
function names, or writable guest memory.

## Runtime contract

`runtime/include/gbrt_port.h` defines:

- exact-ROM module activation and teardown;
- semantic input actions;
- one update per completed guest frame;
- an exact-ROM read-only semantic reader;
- immutable game/ROM metadata;
- host logging;
- bounded renderer-independent panel/text commands; and
- lifecycle/render diagnostics separate from guest state.

The runtime checks module, metadata, and actual embedded-ROM identity before
activation. It hashes the loaded ROM bytes with SHA-256; matching strings or
sizes alone are insufficient.

Port state is held behind one opaque `GBContext` pointer and is destroyed before
the guest context. It is excluded from guest state dumps, savestates,
differential comparison, battery data, and RTC data.

## Crystal module

`ports/pokemon-crystal/module/port-module.json` locks:

- module ID and version;
- port ABI version 1;
- exact Crystal Rev 1 ROM size and SHA-256; and
- the hash of `crystal_port.c`.

Generation validates the manifest, copies the reviewed source and manifest,
compiles the source into `gbrt`, enables the generated main's port lifecycle,
and records the manifest in `crystal-generation.json`.

The M4-003 module slice:

- toggles visibility through `GB_PORT_INPUT_TOGGLE_UI`;
- reads location through the generated M4-002 accessor;
- logs show/hide transitions;
- updates while the guest continues; and
- emits a three-command native overlay when visible.

This is the lifecycle tracer bullet. The complete Workbench content belongs to
M4-004.

## Fail-closed and headless proof

Focused runtime and generated-project tests cover:

- wrong module, host, or metadata ABI;
- a changed actual ROM byte;
- mismatched ROM size/hash;
- duplicate activation;
- rejected or missing module state;
- bounded render-command capacity;
- attach, input, update, render, diagnostics, and detach;
- headless operation with no graphics submit callback; and
- byte-identical guest state with UI hidden and shown.

A synthetic generated project compiled the same `GBRT_ENABLE_PORT_MODULE`
boundary and ran two headless frames. Hidden mode emitted zero commands, open
mode emitted one, and the two guest-state dumps were byte-identical.

## Crystal acceptance

The fresh Crystal executable ran 120 headless frames twice with no graphics
device:

| Mode | Inputs | Updates | Renders | Final commands |
| --- | ---: | ---: | ---: | ---: |
| hidden | 0 | 120 | 120 | 0 |
| open | 1 | 120 | 120 | 3 |

Both guest state files are byte-identical and have SHA-256
`bb0806420a44be20856bfc1d08087b35d7c28f98dcbda5abb74e24097748bd50`.

The module-attached, hidden full route passed all four segments and twelve
checkpoints with zero fallback. Every segment's final guest state is
byte-identical to the accepted M4-002 route.

## Reproduction

```bash
python3 ports/pokemon-crystal/scripts/validate_port_module.py \
  --manifest ports/pokemon-crystal/module/port-module.json \
  --output logs/pokemon-crystal/CR-M4-003/validation-20260729/result.json

cmake -G Ninja -B build . -DBUILD_TESTS=ON
ninja -C build
ctest --test-dir build --output-on-failure

  --output output/pokemon-crystal-m4-port-20260729

  -C output/pokemon-crystal-m4-port-20260729/crystal-build-profile.cmake \
  -S output/pokemon-crystal-m4-port-20260729 \
  -B output/pokemon-crystal-m4-port-20260729/build

  --manifest ports/pokemon-crystal/route/manifest.json \

  --generation-receipt \
    output/pokemon-crystal-m4-port-20260729/crystal-generation.json \
  --evidence-dir logs/pokemon-crystal/CR-M4-003/route-full-20260729 \
```

## Limits

- v1 compiles one reviewed module from source. Dynamic loading and
  multiple-module ordering remain deferred until M6 creates real demand.
- The generic runtime exposes renderer-independent commands; an actual host
  presentation adapter and the complete read-only Workbench belong to M4-004.
- Writable semantic state is intentionally unavailable until M5's
  transactional contracts.

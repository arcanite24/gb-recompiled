## Gate audit

- Discovered functions: exported deterministically in the metadata function
  table.
- Imported names and provenance: every resolved candidate includes
  `source_symbol` and `provenance: imported`.
- Patchability: every function candidate is classified from the metadata
  boolean, not from symbol-file presence.
- Stable IDs: every resolved function candidate's generated
  `gbfn:v1:BBBB:AAAA` ID matches the documented candidate ID.
- State address metadata: every resolved WRAM or SRAM candidate is taken from
  the data-symbol table and receives no ROM function ID.
- Determinism: original and relocated metadata hashes match, and their
  19-candidate snapshots are byte-identical.
- Complete candidate coverage: the script parsed and emitted all 19 rows in
  the semantic-anchor document.
- No symbol-only hooks: `wPartyCount` remains unresolved despite appearing in
  the prepared symbol file; function status requires a generated function
  entry.

## Limits

- `patchable` is a generated-body property, not semantic proof that a symbol
  is the intended gameplay routine. `BillsPC` is the only mechanically
  patchable M1 candidate and is not yet a public hook contract.
- The metadata reports a boolean but no machine-readable reason for an
  unpatchable result.
- The aggressive full-ROM analysis over-discovers code, as documented by
  `CR-M1-002`. M3 must narrow code/data boundaries before promotion of any
  hook.
- Symbol aliases at one address are not all preserved. The unresolved
  `wPartyCount` result is a concrete input to the M3 metadata work.

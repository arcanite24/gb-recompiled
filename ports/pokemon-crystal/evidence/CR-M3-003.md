# CR-M3-003 — Model semantic memory spaces in metadata

Date: 2026-07-29

## Result

PASS. Generated metadata now separates physical ROM, VRAM, external RAM,
WRAM, banked WRAM, HRAM, MMIO, and constant records. Crystal has a reviewed,
exact-ROM semantic-anchor manifest covering map, party, Pokédex, box,
checksum, and MBC3 RTC state. Its validator rejects malformed identities,
spaces, banks, selectors, widths, ranges, and overlaps, and proves that no
non-ROM anchor is exposed as a native function ID.

## Implementation

- `SymbolMemorySpace` classifies the complete CPU address map, including echo
  RAM, OAM, and unusable space in addition to the milestone's required spaces.
- Address metadata carries `memory_space` and `width` through analysis, IR, and
  JSON emission.
- RGBDS constants use a separate `constants` collection with `constant`
  memory-space provenance. They never enter address or function collections.
- Built-in I/O address constants are explicit one-byte MMIO records.
- `semantic/anchors.json` defines 18 reviewed anchors:
  13 address-backed records and the five MBC3 RTC register selectors.
- `validate_semantic_anchors.py` is dependency-free so the repository's system
  Python can run the fail-closed CTest gate.

The raw RGBDS symbol format has no object-size field. Imported address records
therefore retain a conservative width of one byte; the reviewed Crystal
manifest supplies explicit widths for multi-byte structures.

## Limits

- These anchors remain reviewed read-only candidates, not the versioned public
  semantic ABI planned for M4.
- External-RAM symbols outside the supported cartridge's physical banks may
  still exist in the upstream universal/mobile symbol file; the exact-ROM
  Crystal manifest only permits banks 0 through 3.
- The route proves unchanged guest behavior for its recorded coverage, not all
  possible game states.

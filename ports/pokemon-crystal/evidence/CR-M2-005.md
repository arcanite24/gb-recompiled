## Runtime findings and changes

The first fixed-time generated test exposed a real startup bug. Generated
initialization performed:

1. load ROM and persisted battery/RTC data;
2. reset the context;
3. run the game.

The reset zeroed the RTC that had just been loaded. Battery RAM survived only
because reset does not clear external RAM. The corrected lifetime model is:

- creating a context and inserting/loading a cartridge initializes its RTC;
- loading valid MBC3 persistence restores registers and applies wall-clock
  elapsed time;
- CPU/console reset preserves the battery-backed cartridge clock.

The retained platform regression reproduces the generated startup order and
requires two restarts to advance a known `02:03:04 day 1` clock to `02:04:04`
and then `02:05:04`.

Other persistence changes:

- generated executables accept `--rtc-unix-time <seconds>` for deterministic
  wall-clock elapsed-time tests and reject malformed values;
- state JSON exposes RTC registers, cycle remainder, and oscillator state;
- `.sav` and `.rtc` loads stage data before changing guest state and require
  the exact expected size;
- bad RTC magic/version fails visibly;
- a rejected load marks the process unsafe to save, so teardown cannot
  overwrite the rejected input;
- the Crystal generator now defaults to the current root `build/bin/gbrecomp`
  rather than the frozen M1 compiler, with the chosen binary hashed in the
  receipt.

## Vanilla-route isolation

Correct RTC preservation caused the long adventure automation to diverge after
a three-minute inter-process clock offset. The first five checkpoints still
matched, but visual review showed that the old `trainer_battle` golden had
become an overworld frame. The new time-aware hashes repeated exactly, but they
were rejected because the route no longer exercised its named milestones.

The checked manifest therefore makes its original determinism boundary
explicit:

```json
{
  "rtc_unix_time": 1700000000,
  "ignore_rtc_persistence": true
}
```

Each long-route segment starts with clean RTC registers while still loading
battery RAM. Guest RTC cycles advance normally and the resulting `.rtc` file
is still saved. This is disclosed test isolation, not release behavior.
CR-M2-005's restart proof below does not use the isolation flag.

The final isolated route command was:

```bash
python3 ports/pokemon-crystal/scripts/validate_route.py \
  --manifest ports/pokemon-crystal/route/manifest.json \
  --executable \
    output/pokemon-crystal-m2-persistence-final/build/pokemon_crystal \
  --generation-receipt \
    output/pokemon-crystal-m2-persistence-final/crystal-generation.json \
  --evidence-dir \
    logs/pokemon-crystal/CR-M2-005/final-isolated-route-20260729 \
  --fallback-policy ports/pokemon-crystal/route/fallback-policy.json
```

It passed all four segments, 12 checkpoints, state assertions, and the empty
fallback policy:

```text
PASS segments=4 checkpoints=12
```

## Two real RTC restarts

The valid `.sav` and `.rtc` produced by the route were copied into a separate
evidence directory. The checked `restart-continue` input was then replayed in
two new processes without `--ignore-rtc-persistence`:

```bash
pokemon_crystal \
  --headless --no-audio --limit-frames 3500 \
  --input "<checked restart-continue cycle input>" \
  --dump-frames 1500 \
  --dump-state <restart-one-state.json> \
  --save-dir <shared-persistence> \
  --rtc-unix-time 1700003600

pokemon_crystal \
  --headless --no-audio --limit-frames 3500 \
  --input "<checked restart-continue cycle input>" \
  --dump-frames 1500 \
  --dump-state <restart-two-state.json> \
  --save-dir <shared-persistence> \
  --rtc-unix-time 1700007200
```

Both logs explicitly load and save `pokemon_crystal.sav` and
`pokemon_crystal.rtc`.

| Check | Restart 1 | Restart 2 |
| --- | --- | --- |
| Fixed Unix time | `1700003600` | `1700007200` |
| Hardware RTC at exit | `01:01:58` | `02:02:57` |
| Crystal `hRTCHours` | `1` | `2` |
| Crystal `hRTCMinutes` | `1` | `2` |
| Continue frame SHA-256 | `8b986495…89ea` | `8b986495…89ea` |
| Player/map anchors | `17,26,5,1,8` | `17,26,5,1,8` |

The anchors are the same player-state fields asserted by the checked route:
the saved player data, map `26:5`, and coordinates `1,8` survive both clean
process restarts. The one-hour wall-clock increments are visible both in the
MBC3 registers and in Crystal's own HRAM clock snapshot after Continue.

## Limits

- The long route still isolates RTC persistence because its broad periodic
  input is sensitive to time-of-day NPC drift. Real RTC behavior is proven on
  the shorter save/Continue path, not throughout the 620,000-frame adventure.
- This milestone prevents a malformed input from being overwritten in the same
  process. It does not yet provide atomic replace, checksummed envelopes, or
  automatic backup recovery; those remain CR-M5-001.
- The RTC file format is still host-ABI version 1. Cross-version serialization
  hardening remains part of later release engineering.
- The restart proof validates the selected Crystal player/map and clock
  anchors. It is not an independent decoder of every byte in primary and
  backup save banks.

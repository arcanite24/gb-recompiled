# CR-M5-001 — Make battery and RTC persistence transactional

Status: verified

Date: 2026-07-29

## Result

PASS. Battery RAM and RTC writes now stage complete versioned transactions,
flush and synchronize them, and atomically replace the primary file where the
host supports replacement. A failed stage, short write, synchronization,
replacement, or injected interruption leaves the last known-good `.sav` or
`.rtc` untouched. Stale `.tmp-v1` stages are ignored during loading and safely
reused by the next successful transaction.

Crystal's complete route passed all four segments and 12 checkpoints. Its
32 KiB battery file retained matching valid primary and backup game payloads,
the active box, and stable `pokemon_crystal` identity. The new portable RTC v2
format passed two real process restarts while preserving the same Continue
frame and player/map anchors.

## Runtime contract

- Battery RAM stays a raw cartridge-compatible file; Crystal's own primary,
  backup, box, and checksum layout is unchanged.
- A same-directory `<destination>.tmp-v1` stage is opened with truncation,
  written completely, flushed, and synchronized before replacement.
- POSIX uses `rename` plus best-effort directory synchronization. Windows uses
  `MoveFileEx(..., REPLACE_EXISTING | WRITE_THROUGH)`.
- Failed stages are removed. An intentionally interrupted complete stage is
  retained for recovery evidence, but loading only consults the primary file.
- Diagnostics name the persistence kind, transaction version, phase, expected
  and observed byte counts, and state that the prior file was retained.
- RTC serialization v2 is a fixed 40-byte little-endian envelope with explicit
  magic, version, timestamp, cycle remainder, registers, latch state, and zero
  reserved bytes. V1 is accepted and rewritten as v2; unknown versions fail
  closed.

## Failure injection

The repository test invokes the real platform callbacks and hashes the primary
after each injected fault for both battery and RTC targets:

| Fault | Staged result | Durable result |
| --- | --- | --- |
| Short write | 8,191/8,192 or 39/40 bytes | prior primary retained |
| Full disk | rejected before staging | prior primary retained |
| Interruption | complete synchronized stage left behind | prior primary loaded |
| Truncation | half-length stage rejected | prior primary retained |
| Stale stage | junk `.tmp-v1` pre-exists | next complete commit replaces it |

The same test also covers exact-size rejection, unknown RTC versions, v1-to-v2
migration, and automatic-save suppression after a rejected load. Its durable
log SHA-256 is
`a7736c3bb3c7e1551ab2a5ef0f9f136d4aa0ab4102181c1fd656b24addd9cb1a`.

## Limits

- Battery and RTC are each atomic files; there is no cross-file two-phase
  commit. A process interruption cannot corrupt either primary, but this slice
  does not claim an indivisible update spanning both filenames.
- Directory synchronization is best-effort on hosts that do not expose a
  synchronizable directory handle.
- The long canonical route still uses its disclosed RTC-load isolation.
  Actual v2 loading and elapsed-time behavior are proven by the two separate
  real-RTC restart processes.
